# Triage (supervisor)

終わったrunの復旧job。[ADR-0047](../../adr/0047-irregularities-in-three-layers-recovery-job-ask-reasons-and-goal-review.md)の決定39・40（task 441）が、ADR-0044の決定3（task 98）のtriage job（verdictは`retry` / `resume` / `ask`）を復旧jobに置き換えた。`failed` / `interrupted`で止まったrunの次の一手を、supervisorが起動するheadlessの復旧jobが許された操作から選び、runtimeが前提を再検査してから適用する。直せないか自信が無いときだけinboxの`decide`のaskになる。生きているsessionのalert（`long_background`、`stuck_exit`、`prompt_waiting`）は[生きているsessionの復旧job](background-recovery-job.md#生きているsessionの復旧job)が同じverdictで扱う。ラウンドの記録は、ADR-0047の決定40が許すとおりtriageのevent名（`triage_started` / `triage_finished` / `triage_failed`）を使い続ける（`application::supervise::triage`）。

1. **自動recover**: fill passごとに、`active_runs`のうち`integrating`以外でlease行の無いrunについて`doctor`と同じ判定（`run_health`）を行い、`blockers`が空（登録されたwrapper / agentのprocessが無いか、`exited_at`が記録済みか、PIDが死んでいる）なら`recover_run`で`interrupted`にする。`run_recovered`のpayloadは`recover`と同じで、`by: "supervisor"`が付く。taskは`ready`にしない（再実行は復旧jobに委ねる。ADR-0003・ADR-0007の「孤児runは自動再実行しない」は維持し、ADR-0012の「wrapperが死んだrunの`recover`は手動」を`recover`の実行だけ自動に改める）。staleなleaseを持つrunは、leaseのpidが死んでいて、adoptの対象（wrapperが生きているか終了を記録した`running` / `validating`、`resume_skipped`の後のrun、`awaiting_integration`）でなければ対象にする（task 236。supervisorとwrapperが両方死んだrun）。`run_recovered`の`lease_deleted`はtrueになる。leaseのpidが生きている（heartbeatが止まったまま生きているsupervisor）runは対象外。
2. **alert**: `in_progress`のtaskの最新runで`failed` / `interrupted`のもののうち、最後の`resume_started`より後に`triage_finished`も`triage_failed`も無いもの、または最後のラウンドが`wait`でその`recheck_at`を過ぎたもの（`domain::triage_state`が`Pending` / `Waiting`）。alertは、最後の`triage_started` / `resume_started`より後に記録された`recovery_requested`があればその`alert`（resumeを使い切ったrunの`resume_exhausted`。[`needs_session`](needs-session.md#needs_session)の6）、無ければrunのstatusで`failed` / `interrupted`。resumeの後にもう一度`failed`になったrunはもう一度ラウンドを持つ。新鮮なleaseのあるrun（verdictの後の`/exit`を待っているsessionなど）は待つ。active runが上限未満のときだけ始め、jobの間はrun slotを1つ使う。
3. **開始**: 同じrunでそのalertの`recovery_requested`が`MAX_RECOVERY_ATTEMPTS`（3）件に達していなければ、`begin_triage`が`BEGIN IMMEDIATE`の中で上の条件（runがtaskの最新runであることを含む）を再検査し（staleなleaseは置き換える）、runにleaseを取って`lease_acquired`（`reason: triage`）、`recovery_requested`（`alert`、`attempt`（alertごとの通し番号）、`status`、`evidence`（runをそのstatusにしたeventのID）、`last_error`。`resume_exhausted`はruntimeが記録済みなので書かない）と`triage_started`（`attempt`はラウンドの通し番号、`status`、`session_id`）を記録する。同じrunを2つのsupervisorが取ろうとしても1つしか通らない。runのdirectory（無ければ`runs/<run-id>/`）に`recovery-<alert>-<attempt>.prompt.txt`を書き、`AgentProvider::headless_command`（Claudeでは`claude -p --allowedTools Read Grep Glob -- <prompt>`、`triage_started`の`session_id`付き）をそのdirectoryで、`DAGQ_ROLE=reviewer`（queueの読み取りだけを許すreviewの役割を共用する）と`DAGQ_QUEUE`付きで起動し、stdout / stderrを`recovery-<alert>-<attempt>.out` / `.err`に書く。timeoutはreviewと同じ`AgentProvider::review_timeout`（既定600秒）。3件に達していれば、jobを起動せずに`begin_triage`（`recovery_requested`なし）の後すぐ5のescalateにする。
4. **prompt**（`prompt::recovery_prompt`に`prompt::ended_run_material`を足したもの。決定39の入力）: alertとその事実（`recovery_requested`のpayload）、taskのtitle・description・acceptance、runの`last_error`、receipt（末尾3000 byte）、run directoryの最新の`integrate`試行の`integrate-<attempt>-verify-N.log`（N順）とvalidatingが以前書いた`verify-N.log`（あわせて8つまで、各末尾3000 byte。それより前の試行のlogはpathだけ並べる。試行番号の無い旧名`integrate-verify-N.log`は最初の番号付きの試行より前の試行として読む）、`terminal-final.txt`の末尾、そのrunのevent（`events`と同じ圧縮形の直近40件）、同じtaskの他のrun（status、`last_error`、ラウンドの`action`）、worktreeに残るプロセス（cwdがworktreeの下のもの）、worktreeの`git status`とHEADとreceiptの`commit`、そのrunの過去の`recovery_finished` / `auto_repaired`、許された操作（`retry` / `retry_inherit` / `resume` / `wait`）とverdictのschema、許されない操作の一覧、規則（taskの`failed` / `interrupted`のrunが`TRIAGE_RETRY_FAILURES`（2）以上ならretryは適用されない、resumeを使い切っていればresumeを選ばない）。
5. **verdictの適用**（`act_on_recovery`）: stdoutから`RecoveryVerdict`を読む（全体か、最外の`{...}`、未知のfieldは拒否）。`confidence: high`の`repair`で、`actions`がちょうど1つ、かつその前提が今成り立つときだけ適用する（`plan_ended`）。前提:
   - `retry`: taskの`failed` / `interrupted`のrunが2未満で、runのbranchに自分のcommitが無い（`result_commit`、無ければworktreeのHEAD、worktreeを作る前に止まったrunなら無し、がmainの祖先。worktreeが消えていて`result_commit`も無ければ判断できないので崩れとする）。commitのあるrunを最初からやり直すのは成果の破棄なので適用しない。適用するとtaskを`in_progress`から`ready`に戻す（`task_status_changed`）。
   - `retry_inherit`: runのbranchに自分のcommitがあり、そのtaskで引き継ぐretry（`triage_finished`の`action: retry_inherit`）がまだ無い（taskごとに1回。`finish_triage`が同じトランザクションで再検査する）。`refs/dagq/runs/<run-id>`にcommit（`result_commit`、無ければworktreeのHEAD）を残してtaskを`ready`に戻し、`triage_finished`に`inherit`（`branch`、`head`）を書く。次のrunはtask 358の引き継ぎ（`run_inherited`とpromptの「Carried over from run」の節）で始まる。
   - `resume`: resumeを使い切っていない（`ResumeCount::exhausted`でない。通算で数える）、worktreeとreceiptのpathがある。runを`needs_session`にし、`last_error`にjobの`instruction`（空なら`diagnosis`）を書く。[`needs_session`](needs-session.md#needs_session)の自動resumeが拾い、resolution requestは「triageが差し戻した」文面（`ResumeKind::Triage`）で`Reason:`に`instruction`を載せる。
   - `wait`: 何もしない。`recheck_at`（`recheck_after_secs`、上限3600秒）を過ぎたら、runが同じところに居ればもう一度jobを起動する（alertの3回に数える）。
   - `send_instruction`、`stop_processes`、`answer_known_dialog`、`close_and_proceed`はsessionの無いrunには当てはまらないので、前提の崩れとして扱う。
   適用したら`finish_triage`が遷移と`triage_finished`（`attempt`（ラウンド）、`alert`、`recovery_attempt`、`verdict`、`confidence`、`reason`（`diagnosis`）、`duration_secs`、`action`、遷移後の`status`、`resume`なら`instruction`と`code: triage_resume`、`retry_inherit`なら`inherit`、`wait`なら`recheck_at`）、`auto_repaired`（`layer: recovery`、`repair`は操作の名前、`alert`、`attempt`、`conditions`。`wait`には書かない）、`recovery_finished`（`alert`、`attempt`、`verdict`、`confidence`、`diagnosis`、`applied`、`escalated: false`、`recheck_at`、`duration_secs`）を1トランザクションで記録する。適用する前にleaseをまだ持っているかを確かめ、失っていれば（止まっていた間に別のsupervisorが引き継いだ）何も書かずにそのrunを手放す。
6. **escalate**: `escalate`、`confidence: low`の`repair`、前提の崩れた`repair`（操作が1つでない、許されない操作を含む）、alertの3回の使い切りは、`kind: decide`のaskをrunに作る（`asked_by: supervisor`、optionsは`retry` / `resume` / `cancel`（resumeを使い切ったrunは`retry` / `cancel`）にjobの`options`を足したもの、`reason_category`はjobの`discard` / `scope`、それ以外は`recovery_failed`）。questionはalert、escalateの理由（jobが直せなかった、自信が無い、runtimeが適用しなかった理由、使い切り）、`Why a person: <reason_category>`、jobの`diagnosis`、推奨の操作（jobの`actions`）、jobの`question`、`recovery-<alert>-<attempt>.prompt.txt`のpath、`last_error`、各optionの意味（jobの足したoptionは復旧jobにもう一度渡ること）を持つ。askを作った後で`finish_triage`が失敗したら、このpassが開いたaskは取り下げて（`withdrawn: …`と`answered_by: runtime`で答えて）閉じ、8の失敗にする。`ask`を通すのでinboxに`cmux notify`が届く。runはそのまま。`triage_finished`（`action: ask`、`ask_id`、`reason`はescalateの理由とdiagnosis）と`recovery_finished`（`escalated: true`、`why`、`reason_category`、`ask_id`）を記録する。
7. **workspaceのclose**: `triage_finished`の後、runが開いたworkspace（[Run workspaces](run-workspaces.md#run-workspaces)）のうち閉じた記録の無いもので、`cmux workspace list`に居るもの（`WorkspaceBackend::exists`）を閉じ、`workspace_closed`（`workspace_id`、`by: "triage"`、resumeのものなら`resume_attempt`。runのworkspaceなら`workspace_closed_at`も）を記録する。cmuxの失敗は`cleanup_failed`（`workspace_id`、`message`、`by`）に記録して続ける（`last_error`は変えない）。1つでも閉じたら、そのrunの閉じていない`stuck_exit`のaskを閉じる。最後にleaseを解放する。`triage_finished`の後のこれらの失敗（DBのerrorなど）はsupervisor logに書くだけで、`triage_failed`にはしない（verdictは適用済み）。
8. **jobの失敗**: 起動できない、非0終了、timeout、stdoutにverdictが無い、適用中のerrorは`triage_failed`（`code: job_failed`、`attempt`（ラウンド）、`alert`、`recovery_attempt`、`error`、`duration_secs`、`status`）と`recovery_finished`（`outcome: job_failed`、`reason_category: recovery_failed`）を記録してleaseを解放し、runはそのままにする。`triage_failed`はattention（`triage by hand`。ADR-0047は`recover by hand`と読む）で、人がinboxかplannerのsessionから`ready` / cancelなどを打つ。supervisorは同じrunをもう一度ラウンドにかけない（resumeされれば別）。
9. **askの回答**: fill passごとに、`asked_by: supervisor`の`decide`のaskで回答済み・未closeのもの（`triage_answers`）のうち、回答がaskのoptionsにある`retry` / `resume` / `cancel`のどれかで、runが`failed` / `interrupted`でleaseが無いものを`decide_triage`で1トランザクションで適用する（runがtaskの最新runで、askが回答済みかつ未closeであることを中で再検査するので、2つのsupervisorが同じ回答を二重に適用しない。staleなleaseの行は同じトランザクションで消すので、止まっていたラウンドのsupervisorが起きてもleaseを更新して書けない。[ADR-0039](../../adr/0039-adopt-stale-lease-of-live-wrapper-and-renew-own-stale-lease.md)の決定7）: `retry`はtaskを`ready`（人の判断なので、commitのあるrunでもよい）、`resume`はrunを`needs_session`（`last_error`は直近の`triage_finished`の`reason`に「ask Nで人がresumeを選んだ」を添えたもの。`ResumeKind::Triage`でresumeされる）、`cancel`はtaskを`canceled`にし、askを閉じ、`triage_decided`（`ask_id`、`answer`、`reason`、`status`）を記録する。taskが既に`in_progress`でないか、より新しいrunがあれば（人が`ready`を打ったなど）適用するものが無いのでaskを閉じるだけにする。回答がjobの足したoption（askのoptionsにあり`retry` / `resume` / `cancel`でないもの）なら、何も動かさずにaskを閉じ、`triage_decided`（`action: recover`）を記録する。`triage_state`はこれを`Pending`と読むので、次のfill passで同じalertのラウンドがもう一度始まり（alertの3回に数える）、その`recovery_requested`の`person_answer`（`ask_id`、`answer`）とpromptのalertの事実でjobが人の選んだものを読む。optionsに無い自由な回答は人が読む（`read the answer of ask N and close it`）。`answer`はこの条件（optionsのどれか）のaskの`ask_answered`に`runtime_delivers: true`を書き、attentionにしない（`status`では`applying the answer of ask N (runtime)`）。
