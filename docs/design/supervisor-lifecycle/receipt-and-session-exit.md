# Receipt and session exit

receiptの受領とセッション終了は別の事象である。agentはreceiptを`<run-dir>/receipt.json`へ一時ファイルからrenameして公開し、応答完了後もセッションを維持する。セッション終了はwrapperが記録する終了コード（`session_exited`）だけで確認し、画面文言は使わない。

receipt受領後の流れは次の順で自動化している。[ADR-0027](../../adr/0027-keep-worker-session-through-review-revise-verdict-and-merge-tree-precheck.md)の決定1で、idleになったsessionにはすぐ`/exit`を送らず、sessionを開いたまま[Validation](validation.md#validation)と[Review](review.md#review-supervisor)に進み、`/exit`はverdictが出た後に送る。

1. **idle判定**: Claude adapterがrunごとの`<run-dir>/claude-settings.json`に`Stop` hookを書き、`--settings`で渡す。hookはClaudeが応答を終えるたびにstdinのイベントJSON（`session_id`、`hook_event_name`など）を`<run-dir>/idle.json`へ一時ファイル + renameで書き、置き換える前に同じ内容を時刻付きで`<run-dir>/idle.log`へ追記する（`long_background`の経過の起点。[stats](stats.md#stats)）。supervisorはreceiptを観測した後、`idle.json`のmtimeが`receipt.json`のmtime以上で、markerの`background_tasks`に`status`が`running`の要素が無ければ「receipt提出後に応答が完了した」と判定する。receiptより古いmarker（質問で止まった以前のturnなど）は無視する。**idleの定義**（task 147。`IdleMarker`。markerの内容の読み取り、つまり`background_tasks`と記録するhookのフィールドはClaude Code固有の形式なので`AgentSignals::idle_hook`（`infrastructure::claude`）が行い、mtimeとreceiptの比較はapplicationが行う）: Stop hookのmarkerがあり、その`background_tasks`に`running`の処理が無いこと。Claude Code（2.1.281で確認）はbackgroundの処理（`run_in_background`のshellなど）を残してturnを終えてもStop hookを発火し、入力JSONの`background_tasks`に`{id, type, status: "running", description, command}`を載せる。その間に`/exit`を送ると「Background work is running」の確認画面が出て、処理が終わっても誰かが答えるまで消えない。処理が終わるとClaude Codeは自分でturnを再開し、Stop hookが`background_tasks: []`で再び発火するので、supervisorはそのmarkerを待つ。`background_tasks`の無いmarker（古いClaude Code）は従来どおりidleとみなす。markerのmtimeと内容は1つのopenしたfileから読む（hookはrenameで置き換えるので同じ書き込みのものになる）。画面は読まない（ADR-0016のTUI非結合）。この定義は、最初のsessionのidle、resumeの(i)(ii)、reviseの書き直し、verdictの後の`/exit`で使う（[workerの質問への回答の送信](worker-question-answer.md#workerの質問への回答の送信)は従来どおりmarkerのmtimeだけを見る。promptへの打ち込みは確認画面を出さず、`/exit`だけが出すため）。終わらないbackgroundの処理でrunが無期限に止まらないよう、最初のsessionはreceiptを観測してから`resume_timeout`（既定1時間）過ぎれば、`running`の処理が残っていてもreceipt以上に新しいmarkerで先へ進む（`session_idle_observed`の`background_running: true`。その後の`/exit`は下の2のとおりもう一度待ち、確認画面で止まれば3の`stuck_exit`のaskになる）。判定の根拠（両ファイルのmtime、hookのフィールド、`background_running`）は`session_idle_observed`に記録する。権限確認や質問で止まっているturnでは`Stop`が発火しないため、その間は先へ進まない。idleと判定したら`finish_supervision_live`でrunを`running`から`validating`にし（`supervision_finished`の`{"status":"validating","exit_code":null,"session_live":true}`）、同じleaseのまま検証に進む。sessionは開いたまま。
2. **終了要求**（verdictの後。[Review](review.md#review-supervisor)の5）: idle markerが`running`のbackgroundの処理を示している間は送らずに待ち（receiptの後にsessionが別のturnでbackgroundの処理を始めた場合。上限は`ExitWatch`を始めてから`resume_timeout`で、過ぎれば送り、確認画面で止まれば下の3の`stuck_exit`のaskになる）、logに1回だけ書く。`WorkspaceBackend::send_exit(workspace_id)`で、cmuxでは`cmux send --workspace <uuid> -- /exit`の後に`cmux send-key --workspace <uuid> -- enter`を送る。人が打つのと同じ経路で、1回だけ送り、プロセスのkillはしない。cmuxの時間切れで`/exit`が届かなかったと画面で分かるときだけ、backoffを置いて`call_attempts`回まで送り直す（task 354。[backendの呼び出しの失敗](backend-call-failures.md#backendの呼び出しの失敗)のtimeoutのretry）。全試行が届かずに終わったら（`Submission::Unsent`）、`exit_timeout`を待たずに（sessionは終了を頼まれていない）`exit_unsent`（`code: backend_timeout`、`workspace_id`、`attempts`、`action`、`close_and_land`でないときは理由の`held`）を記録し、次の条件がそろえばworkspaceを閉じて（sessionはそれで終わる。`workspace_closed`を記録し、sessionの`answer_prompt`のaskを閉じる）sessionが終わったものとして進む（`action: close_and_land`。[Review](review.md#review-supervisor)の5の着地へ。workspaceを閉じられなければ着地せず、下のaskにする）: verdictの後の行き先が着地（reviewがpass、または承認された解消済みのresume）であること、`check_receipt`（validationと同じ検査）が通ること、つまりreceiptの`commit`がworktreeでcheckoutされたrun branchのHEADで、worktreeがcleanで、evidenceとscopeが満たされていること、そのHEADがreviewしたcommit（`result_commit`。無ければ進まない）であること。どれかが欠ければ（`action: ask`）、`exit_request_timed_out`（`unsent: true`付き）を記録して下の3と同じ`stuck_exit`のaskを直ちに作り（questionの`after`の頭に届かなかったことと`held`の理由が入る）、runは手放さずにsessionの終了を待つ。`ExitWatch`以外の`/exit`（走行中のsessionやresumeのsession、runtimeのplanner）は`Unsent`を無視して従来どおり`exit_timeout`を待つ。`exit_requested`（`timeout_secs`付き）は送る前に記録する。sessionは`enter`で即座に終わり得て、wrapperの`session_exited`が`send_exit`の戻りより先にcommitされることがあるので、送った後に記録するとイベントの順序が因果と逆になる。送信の失敗はrunをabandon（leaseを外す）するので、引き継ぎの対象にならない。記録と送信の間でsupervisorが死んだ場合だけ、引き継いだsupervisorは`exit_requested`を見て`/exit`を送らず、runは`exit_request_timed_out`まで待って人の`/exit`を待つ（送った後に記録していたときは逆に`/exit`を2回送り得た。2回送らないことを優先する）。
3. **終了確認**: wrapperの`session_exited`を待ち、workspaceを閉じて次へ進む（[Review](review.md#review-supervisor)の5）。ADR-0027より前のsupervisorが`/exit`を要求済みのrunを引き継いだときは、従来どおり`session_exited`を待って`supervision_finished`へ進む。要求から`WorkspaceBackend::exit_timeout`（cmuxは120秒）以内に終了しなければ、`exit_request_timed_out`（`workspace_id`、`timeout_secs`）を1回だけ記録してlogに書き、そのrunを手放さずに監視を続ける（ADR-0019の決定2）。runはそのときのstatus（verdictの後なので`awaiting_integration` / `needs_session` / `failed`。前の経路で引き継いだrunは`running`）のままleaseも保持し、`last_error`と`runtime_error`は書かない。Claude Code自身のダイアログなどが`/exit`を止めた状態を想定しており（典型は、workerが残したbackgroundのshellや待ちループに対する「Background work is running」の確認画面。promptとresumeの依頼が`STOP_BACKGROUND`で予防する。[Prompt](prompt.md#prompt)）、`/exit`は再送しない（開いたダイアログの別の選択肢を押しかねないため）。記録と同じpollで、supervisorはinbox宛ての`kind: stuck_exit`のaskを作る（task 104。常駐sessionの退役で`send /exit`のattentionを拾う役が居なくなるため、ADR-0019の決定2の「timeoutで人に知らせる」を[ADR-0022](../../adr/0022-ask-answer-inbox-planner-and-landing-on-doubt.md)の決定5の枠組み（通知はaskだけ）で行う）。askはtaskとrunに紐づき、`asked_by`は`supervisor`、optionsは`exit`（ダイアログに応答してsessionを終わらせ`/exit`を送る）と`wait`（sessionをそのままにする）で、questionは人に宛てて、run id・task id・timeoutの秒数・workspace id・sessionが終わった後にrunがどう進むか（`running`なら`validating`へ、verdictの後なら着地・`approve_landing`のask・review by hand・resume・人への引き渡しのどれか。`ExitWatch::after`）・2つの選択肢の意味と、`WorkspaceBackend::capture`で読んだ画面の末尾15行（空行を除く。[ダイアログ待ちの検知](prompt-waiting.md#ダイアログ待ちの検知)の`excerpt`と同じ`screen_tail`。読めなければその旨）を持つ。同じ（run、kind）のopenなaskがあれば作らず（askの重複抑止）、通知は新しいaskのときだけaskの経路で1回inboxへ送る（[人への通知](cmux-notify.md#人への通知cmux-notify)）。引き継いだrunは、`exit_request_timed_out`が記録済みで`stuck_exit`のaskが（closeされたものも含めて）1件も無いときだけ作る（記録とaskの間でsupervisorが死んだ場合と、askを作らない前のversionのbinaryが記録したtimeout）。`exit_request_timed_out`のイベント自体はattentionではなく（`event_attention`は`None`。kind名とpayloadはそのまま記録する）、`status`もこのrunをrunのattentionに出さない（`run_attention`は`exit_pending`の`running`に`None`を返し、その前の`prompt_waiting`も出さない）。人に届くのは`stuck_exit`のaskの`ask_opened`（`answer ask <id>`、role inbox）で、`send /exit`の`next`は無くなった（`AttentionNext::SendExit`を消した）。inboxは人に見せてanswerを書き戻し、その`ask_answered`（`read the answer of ask <id> and close it`）を受けて、人の指示として`dagq-recover` skillの`reference/stuck-exit.md`に従って動く: 画面を読み、「Background work is running」なら worktreeがcleanでreceiptの`commit`がHEADを指すことを確かめてから「Exit and stop tasks」を選び（確かめられなければ選ばず人に確かめる）、ほかのダイアログは人の選んだキーで応答してから`/exit`を送る。`wait`ならsessionに触らず`ask close`する。人がsessionを終わらせれば、wrapperの`session_exited`を観測した時点で、supervisorはそのrunのcloseされていない`stuck_exit`のaskを閉じてから（未回答なら`answer`に`the session exited; closed by the runtime`を書いて`ask_answered`（`ask_id`、`kind`、`runtime_closed: true`）を記録する。`runtime_closed`の`ask_answered`はattentionではない。回答済みなら`closed_at`だけ）、runを進める: `running`（前の経路）なら通常どおり`supervision_finished`→`validating`へ、verdictの後なら[Review](review.md#review-supervisor)の5のとおりworkspaceを閉じて着地・`approve_landing`のask・`review_failed`・resume待ち・`failed`のまま（workspaceは残す）のどれかへ。wrapperのheartbeatが切れた場合は、wrapperのプロセスが死んでいれば従来どおりabandon（下記）、生きていれば下の[wrapperが黙ったsession](silent-wrapper.md#wrapperが黙ったsession)になる。supervisorがleaseを持っている間は`recover`が拒否されるので、人が止めるときは`down --force`でsupervisorを止めてから`recover`する経路も変わらない。引き継いだrunは`exit_request_timed_out`が記録済みなら再記録しない。このrunはsessionが終わるまでslotを占め、drain（`down --wait`、SIGINT / SIGTERM、`up`によるversionの入れ替え、`--once`）もそのrunを待ち続けるので、drainの前に`stuck_exit`のaskを片付けてsessionを終わらせる（待てなければ`down --force`）。

人の手動`/exit`はいつでも有効で、markerがない（hookが無効化されているなど）場合は従来どおり手動終了を待つ。sessionがreceiptの後に自分で終わった場合は、wrapperの`session_exited`から`supervision_finished`（`exit_code`付き）→`validating`へ進み、reviewでは`/exit`を送らずにworkspaceを閉じる。ただし生きているsessionが無いので、`revise`は人に聞く（`approve_landing`）。
