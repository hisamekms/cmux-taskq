# Plan review (supervisor)

[ADR-0044](../../adr/0044-findings-proposals-from-findings-and-quiet-observer.md)の決定10〜15・17（task 281）。submitされたproposalを、supervisorが起動するheadlessのplan review jobが検査し、そのverdictと人のanswerをruntimeが適用する。use caseは`src/application/supervise/plan_review.rs`、storeは`src/infrastructure/plan_reviews.rs`（port `PlanReviewStore`）、verdictの型と順序は`src/domain/plan_review.rs`。run slotは使わず、observerと同じくloopの各passで進める（`--once`のloopは走っているplan reviewを待ち、passでverdictかanswerを適用したらもう1 pass回ってreadyになったtaskをclaimしてから終わる。`--once`で立てたplannerは終わらせない）。drain中（`stop`、provisioningの失敗）は新しいplan reviewを始めず、reviseの配送もしない（走っているjobとanswerの適用は続ける）。

1. **記録**（schema v27、`migrations/0027_plan_review.sql`）: jobは`plan_reviews`の1行（`proposal_id`、`attempt`、`supervisor_token`、`dir`、`started_at`、`finished_at`、`outcome` = `pass` / `revise` / `concern` / `failed` / `interrupted`、`verdict`のJSON、`error`）。未完了の行は部分unique indexで1つまでなので、queue全体で同時に1つ。`proposals`に`review_hold`（`failed` / `concern`: plan reviewが自分では取り直さない）、`revise_reasons`（plannerに渡す指摘のJSON配列）と`revised_at`（差し戻した時刻）、`revise_sent_at` / `revise_planner_id`（配送を取った時刻と渡した相手。nullならまだ渡していない）、`unresponsive_at`を足した。`submit`（出し直しを含む）はこれらをすべて消す。askのkindに`approve_plan`を足した。eventはrun_eventsがtaskかgoalを要るので、proposalの最初のtask（ID最小）に`proposal_id`付きで記録する。
2. **順序**（`next_to_review`）: 対象は`submitted`で`review_hold`が無く、`submitted`のtaskを持つproposal。`interrupt`の優先度のsubmittedのtaskを持つものが先、次にsubmitの古い順、次にID順。gateは飛ばさない。
3. **開始**（`begin_plan_review`、`BEGIN IMMEDIATE`）: 未完了の行があり、そのsupervisorの登録が生きていれば（heartbeatが30秒以内）始めない。そうでない行は`interrupted`で閉じる（supervisorが死んだjobの引き継ぎ）。対象であることを再検査し、行を作って`<queue dir>/plan-reviews/<行のID>/`を`dir`にし、`plan_review_started`（`proposal_id`、`plan_review_id`、`attempt`、`dir`、`session_id`、jobを起動するrepositoryのcheckoutの`cwd`、proposalの特徴の`features`（`{origin, follow_up_depth, related_score, related, revise_count}`。task 579、書き込みのロックの前に読み、読めなければnull。規則は[kpi](kpi.md#計画の品質)））を記録する。promptを`prompt.txt`に書き、`AgentProvider::headless_command`（Claudeでは`claude -p --allowedTools Read Grep Glob -- <prompt>`）をrepositoryのcheckoutで、`DAGQ_ROLE=reviewer`と`DAGQ_QUEUE`付きで起動し、stdout / stderrを`review.out` / `review.err`に書く。timeoutは`AgentProvider::review_timeout`。
4. **prompt**（`plan_review_prompt`）: 最初にrepositoryのAGENTS.md / CLAUDE.md、`docs/adr/README.md`、taskが名指すADRと設計文書を読んで反映せよと指示する（verificationの規則やADRのIDの形をruntimeに埋め込まない）。材料はproposalのtask（全field、依存、goalへの依存）、関係するgoal（description・acceptance・constraints。constraintsがtaskのdescriptionより優先）、`dagq lint`の結果（`domain::lint::lint`）、他の`submitted` / `revising`のproposalとそのtask（このproposalより前に出されたか後か）、`ready` / `in_progress`のtaskの要約（task 591。ID降順に200件（`QUEUED_TASKS`）までで、超えて落とした件数をpromptに書く。1taskにつき1行のJSONで`id`・`status`・`priority`・`goal_id`・`title`・`paths`・`dependencies`・`goal_dependencies`・予想するファイルの`expected_files`（`SUMMARY_EXPECTED_FILES`（10）件まで、超えた数は`more_expected_files`）。description・acceptance・contextなどの全文は、proposalの各taskの重複の候補（下の`related`と`search`）に載ったtaskと、proposalのtaskと同じhotspotを触ると予想されるtaskにだけ、別の節に付け、要約に`full_text_below`を付ける）、proposalの各taskの予想するファイル（1taskにつき1行）、人が答えたask（新しい順に30件、先例の候補）、衝突の多いファイル（`stats`の既定のwindowの`conflict_hotspots`のうち`deleted`でないもの15件まで。renameされたものは今の名前で、`conflicts`・`tasks`・`landings`・`ratio`・`last_conflict_at`・`alert`。supervisorは`LoopSettings.conflicts`（起動時にmain checkoutの`dagq.toml`の`[conflicts]`を読む）とsupervisorの`Repository::main_history`で数える。goal 31。各ファイルに、触ると予想されるproposalのtaskの`proposal_tasks`と`ready` / `in_progress`のtaskの`queued_tasks`を並べる。task 591）、proposalの各taskの重複と実装済みの候補（goal 29、task 401。taskごとに1行のJSONで、`related`は`dagq related`と同じ`SqliteQueue::related`（port `RunStore::related_tasks`）が返す関連の強いtaskを状態を問わず理由（`clues`）・`score`・`status`付きで、`search`は`dagq search`と同じ`SqliteQueue::search`（port `RunStore::search_documents`）でtaskのtitleの語（3文字以上の英数字と`_ - . /`の並び、20語まで、`domain::search::any_word_query`でORに組む）を引いたtaskと着地したcommitのhitを`status`・excerpt付きで。どちらも`DUPLICATE_CANDIDATES`（5）件までで、proposal自身のtaskとそのcommitは除き、候補が無ければ空の配列）。重さの予測（ADR-0079の決定2、task 575）として、verdictに関わらずproposalの`submitted`のtaskごとに`size`・`nature`・`uncertainty`・`expected_output_tokens`・`rework_probability`・`reason`を出せと指示し、対象のtaskのIDと目安（worker 1 runの出力tokenは小さいもので5千、大きいもので25万、中央値3.5万。スパイクの`scripts/spikes/predictor-replay/predict.py`のもの）を書く。予測のために別のmodelは呼ばない。**予想するファイル**は[claimを控える](claim-defer.md#判定の入力)と同じ規則と関数（ADR-0069の決定1・2）で求める: 宣言`paths`、無ければ`dagq related`で最も似た`completed`のtask 3件の着地commitが変えたファイル（`Supervisor::expected`、`domain::claim_defer::expected_files`。cacheを共有し、proposalのtaskはplannerが`paths`を変えうるのでcacheを捨てて読み直す）、`in_progress`のtaskはさらにそのrunのbaseからheadまでの差分（`Supervisor::runs_in_flight`）。hotspotに当たるかは`domain::claim_defer::touches`（globのまま）。意味の検査として、重複と実装済み（候補を手がかりに、completed・canceledのものも見てLLMが判断する。明らかな重複だけを`cancel_duplicate`にし、疑わしいもの・実装済みに見えるものは`concern`）、ADR・constraintsとの矛盾、**acceptanceとdescription・兄弟taskのacceptanceの食い違い**（型を変える変更なのに「tests/cli.rsは変えない」など）、同じファイルを触るtaskの間の依存（とくに衝突の多いファイル。`proposal_tasks`と`queued_tasks`がどちらも空でないhotspotには、依存の追加（`add_dependency`）か要らない理由をsummaryに書かせ、proposalのtaskが触るファイルはsourceから確かめてよいとする）、`ready` / `in_progress`のtaskと一部だけ重なるtask（片方の範囲を削れば済むもの）は`pass`にせず`revise`にし、どの範囲を削るか・どちらに寄せるかをreasonに書く（疑わしい重複は`concern`、明らかな重複は`cancel_duplicate`のまま。ADR-0044の決定11）、先に出されたproposalとの食い違い（後に出されたものとの食い違いならこちらは通す）、変える必要のあるreadyのtask（`reopen`）、`in_progress`のtaskは直さず着地後に直すtaskを求める`revise`、lintの指摘を挙げる。同じ種類の指摘に人が答えたaskがあれば、そのIDを`precedents`に入れ、reasonに人の答えを書く。
5. **verdict**（`PlanReviewVerdict`、全体か最外の`{...}`、未知のフィールドは拒否）: `{"verdict": "pass" | "revise" | "concern", "reasons": [...], "summary", "actions": [...], "reopen": [{"task_id", "reason"}], "precedents": [ask id], "predictions": [{"task_id", "size": "S" | "M" | "L", "nature": "mechanical" | "implementation" | "design_judgment" | "investigation", "uncertainty": 0〜1, "expected_output_tokens": 正の整数, "rework_probability": 0〜1, "reason"}]}`。`predictions`は未知のフィールドの拒否の対象外で、どんな形でもverdictの解釈を失敗させない（生のJSONのまま受け、6で検査する。`domain::prediction::parse_predictions`）。`actions`は`add_dependency`（`task_id`、`depends_on`）/ `lower_priority`（`task_id`、`priority`）/ `cancel_duplicate`（`task_id`、`duplicate_of`）だけで、`pass`のときだけ適用する。
6. **適用**（`finish_plan_review`、1トランザクション）: 行がまだ自分の未完了の行でなければ何もしない。proposalがもう`submitted`でないか保留されていれば、行を`interrupted`で閉じて何もしない。jobの開始（その`plan_review_started`のevent）より後にproposalのいずれかのtaskに`task_edited`があれば（[ADR-0041](../../adr/0041-on-demand-planners-proposals-submitted-and-plan-review-job.md)の決定9。eventのIDで前後を比べる）、verdictはpass / revise / concernのどれも古い内容へのものなので適用しない。行を`interrupted`で閉じて（`verdict`は残し、`error`に`task N of the proposal was edited during its review`）、`plan_review_discarded`（`proposal_id`、`plan_review_id`、`attempt`、`verdict`、`edited`、`error`）を記録する。proposalは`submitted`で保留もないままなので、次のpassで編集後の内容をplan reviewにかけ直す（`interrupted`の行は`attempt`に数えない）。検査中でないsubmittedのtaskの編集と、他のproposalのtaskの編集は、verdictの適用を妨げない（次のplan reviewが新しい内容を読む）。runtimeは`revise`で`revise_count`が2（`MAX_PLAN_REVISES`、runのreviewと同じ）以上なら`concern`にする（`overridden`）。`precedents`のaskは`precedent: ask N (kind) asked: … — a person answered: …`の行にして、reviseの指摘の後ろとconcernのaskのquestionに足す。
   - `pass`: 各actionを先に検査し（proposalの`submitted`のtaskであること、依存先が存在し自分でないこと、優先度は下げるだけ、重複先がcancelされておらず同じverdictで重複としてcancelされるものでもないこと）、1つでも外れればverdict全体を失敗（下の7）にする。通れば依存を足し（`dependency_added`）、優先度を下げ（`task_priority_changed`、`by: plan_review`）、重複をcancelし（`task_canceled_as_duplicate`、`duplicate_of`）、proposalを`accepted`、submittedのtaskを`ready`にし、draftのgoalを開く。
   - `revise`: proposalを`revising`（taskは`draft`、`revise_count`+1）にし、指摘を`revise_reasons`に置いて配送を待たせる（下の9）。
   - `concern`: `review_hold = concern`にし、`approve_plan`のask（proposalの最初のtask、runなし、`asked_by: plan_review`、options `ready` / `send_back` / `cancel`、questionにsummary・上書きの理由・reasons・先例・`prompt.txt`のpath）を同じトランザクションで作り、適用の後にinboxへ`cmux notify`する。
   - `reopen`（verdictに関わらず）: proposalに無く、`submitted` / `revising`の他のproposalにも属さない`ready`のtaskを`submitted`に戻し（`TaskAction::Reopen`。claimされない）、そのtaskだけの新しいproposal（`revising`、`owner_origin: runtime`、workspaceなし、`revise_count` 0）に入れ、理由を`revise_reasons`に置き、`task_reopened`（`proposal_id`、`reviewed_proposal_id`、`reason`）を記録する。`ready`でないtask（`in_progress`など）と、検査中・差し戻し中のproposalのtaskは変えず、`plan_review_finished`の`reopen_skipped`に理由を残す。出し直し（`submit --proposal`）はproposalの`submitted`のtaskもそのまま持って出す。
   - 最後に行を閉じ、`plan_review_finished`（`proposal_id`、`plan_review_id`、`attempt`、`verdict`、`decision`、`overridden`、`reasons`、`summary`、`actions`、`reopened`、`reopen_skipped`、`precedents`、`ask_id`、`duration_secs`、`prediction_error`）を記録する。
   - **重さの予測**（ADR-0079の決定2、task 575）: `pass` / `revise` / `concern`のどれでも、適用の前にproposalの`submitted`だったtaskに対して`predictions`を検査する。無い、配列として読めない、taskが足りない・余る・重なる、`size` / `nature`が知らない値、`uncertainty` / `rework_probability`が0〜1の外、`expected_output_tokens`が正の整数でない、のどれかなら予測は1件も記録せず、理由を`plan_review_finished`の`prediction_error`に残す（通れば`null`）。verdictの適用はそのまま行う。通れば`plan_review_finished`の後に、taskごとに`task_weight_predicted`（taskに付け、`proposal_id`、`plan_review_id`、`attempt`、`prediction`（`size`、`nature`、`uncertainty`、`expected_output_tokens`、`rework_probability`、`reason`）、`model`、`effort`）を記録する。`model` / `effort`は`plan_review_finished`が閉じたjobのsessionの`session_closed`のもの（transcriptから読めなければnull）。出し直しや`reopen`でかけ直したtaskには新しい予測を上書きせず追記し、読む側は最後のものを使う（[stats](stats.md#重さの予測と実績)）。検査中の編集で捨てたverdict（`plan_review_discarded`）と失敗したjobの予測は記録しない。claimは予測を作らず、workerの起動のmodel / effortも変えない。
7. **失敗**（`fail_plan_review`）: 起動できない、非0終了、timeout、stdoutにverdictが無い、verdictを適用できない（許されないaction、proposal内のtaskの`reopen`）は、行を`failed`で閉じ、`review_hold = failed`にして`plan_review_failed`（`code: job_failed`、`proposal_id`、`attempt`、`error`、`duration_secs`、`status: submitted`）を記録する。proposalは`submitted`のまま動かさず、supervisorは同じproposalを自分では取り直さない。`plan_review_failed`はattention（`plan review by hand`）で、`status`の`attention`にも保留が解けるまで出る（`concern`で保留したのに`approve_plan`のaskが自由記述の回答で閉じられたproposalも同じattentionになる）。人の指示で、inboxがtaskを`ready --bypass-review`にするか、plannerかinboxが`dagq submit --proposal N`を打つ。保留中のproposalはtaskとgoalを足さずにそのまま出し直せ（`proposal_resubmitted`、submitの時刻が新しくなる）、plan reviewにかけ直される。
8. **片付け**（`settle_proposals`、各pass）: `submitted`なのに`submitted`のtaskが1つも無くなったproposal（人がbypassで`ready`にした、cancelした）は、jobが走っていなければ、cancelされていないtaskが残れば`accepted`、無ければ`canceled`にし、保留を消して`proposal_settled`を記録する。goalとtaskが他のproposalに入れるようになり、attentionも消える。
9. **reviseの配送**（`tend_planners`、各pass）: plannerが終わったかは`planner_view`で決め、`exited`か`lost`（wrapperのheartbeatが止まった）、または`cmux workspace list`に居ない上でwrapperも死んでいるものだけを終わったとみなす（居ないだけでは証拠にせず、workerと同じくwrapperで判定する）。まず差し戻し中のproposalを見て、渡した相手のplannerが終わっていれば`plan_revise_lost`を記録して未配送に戻し、終わっていないのに`--planner-timeout`（既定3600秒）を過ぎても出し直されていなければ`planner_unresponsive`（`planner_id`、`waited_secs`）を記録する。まだ誰にも渡せていないreviseも、`revised_at`から期限を過ぎれば`planner_unresponsive`（`planner_id: null`）にする。どちらも1回だけで、attentionは`check the planner`、workspaceは閉じない。配送を取ったまま記録の無いもの（supervisorが間で死んだ）は30秒後に未配送に戻す。次に未配送のreviseをproposalのID順に配る。持ち主のworkspace（`owner_workspace_id`）のplannerが生きていれば、`idle`になるのを待ち、`claim_revise`（`revise_sent_at`がnullの行だけを条件付きUPDATEで取る。2つのsupervisorが同じreviseを二重に配らない）で取ってから`plan_revise_request`（指摘、先例、`dagq submit --proposal N`で出し直すこと、意図の変わる修正は人に聞くこと）を`submit_input`で打ち込み、`plan_revise_sent`（`planner_id`、`workspace_id`、`opened: false`）を記録する。打ち込みが失敗すれば取った配送を戻す。持ち主が居ないか終わっていれば、runtimeが立てたplannerで生きているものが`--runtime-planners`（既定1、run slotとは別。人が開いたplannerは数えない）未満のときだけ、配送を取って`open_runtime_planner`で新しいplannerを立て（初期promptに指摘）、`plan_revise_sent`（`opened: true`）を記録する。上限に達していれば待つ。持ち主のworkspaceが一覧に居ないのにwrapperが生きているときも待つ（期限でinboxに届く）。reviseを配った後、同じ上限の残りでruntimeやjobが作ったdraftのplannerを立てる（[Draft planners (supervisor)](draft-planners.md#draft-planners-supervisor)）。
10. **runtimeが立てたplannerの終わり**: runtimeが立てたplannerのうち、終わったものはworkspaceが`cmux workspace list`に居れば閉じ、行を`close_planner`で閉じる。`idle`で、自分宛てのreviseが残っていない（proposalを出し直した）ものには1回だけ`/exit`を送り、終了が記録された後のpassで上のとおり閉じる。`/exit`から`WorkspaceBackend::exit_timeout`を過ぎても終わらなければworkspaceを閉じて行を閉じる。人が開いたplannerはruntimeが閉じない。
11. **answer**（`decide_plan`、1トランザクション）: 回答済み・未closeの`approve_plan`のask（`plan_answers`）のうち、回答が`ready` / `send_back` / `send_back: <理由>` / `cancel`で、askのtaskのproposalがまだ`submitted`で`review_hold = concern`のものに適用する。`ready`はproposalを`accepted`にしてtaskを`ready`、`send_back`は`revising`にして`revise_reasons`を「人がask Nで差し戻した: <理由>」と直近のverdictのreasonsにし（配送は9）、`cancel`はproposalを`canceled`にしてsubmittedのtaskをcancelする。askを閉じて`plan_decided`（`proposal_id`、`ask_id`、`answer`、`status`）を記録する。proposalが動いていればaskを閉じるだけ。それ以外の回答は適用せず、`ask_answered`の`runtime_delivers`が`false`なので`read the answer of ask N and close it`のattentionになる。適用できる回答は`runtime_delivers: true`で、`status`では`applying the answer of ask N (runtime)`。
12. **設定**: `supervise --runtime-planners N`（既定1）、`--planner-timeout SECS`（既定3600）、`--plugin-dir PATH`（runtimeが立てるplannerが読むplugin）。`up`は自分の`--plugin-dir`をsupervisorにも渡す。
13. **test**: `tests/it/plan_review.rs`がstubのheadless provider（台本のverdictを印字する）とcmuxのdoubleで、pass（actionの適用とprompt）、生きているplannerへのrevise（acceptanceとdescriptionの食い違いの指摘と、先例の回答が載ること）と期限切れのinboxへの通知、閉じたplannerの代わりにruntimeが立てるplannerと同時の数の上限（上限で待つreviseの期限切れを含む）、concernのaskとanswer（`ready` / `send_back: 理由` / `cancel`）の適用、reviseの上限超え、jobの失敗と適用できないverdict、保留したproposalの出し直しとbypassによる片付け、interruptの先行、readyのtaskの`reopen`（claimされず、runtimeのplannerが直して出し直す。検査中のproposalのtaskは動かさない）、promptの`ready`のtaskの要約と全文の付き方（同じhotspotを触る`ready`のtaskがあるqueueでは、hotspotの行に両方のtaskが並びそのtaskだけ全文が付き、無いqueueでは`queued_tasks`が空で全文が付かない。`src/application/prompt.rs`の単体testは、落とした件数の表示と、長いfield（約3KB）のreadyのtask 170件で全文の約58万byteに対しpromptが約4.7万byte（8分の1未満）に収まることを確かめる）、promptに載る重複と実装済みの候補（relatedのcompletedのtask、searchのcompleted・canceledのtaskと着地したcommitが載り、proposal自身のtaskは載らず、似たもののないtaskは空）、検査中に編集されたtaskのproposalのverdict（pass / revise / concern）を適用せずに編集後の内容でかけ直すこと（stubのjobが実行中に`edit_task`する。検査の前の編集と他のproposalのtaskの編集は適用を妨げない）、重さの予測がtaskごとに記録され、足りない予測と形の崩れた予測は記録されずに`prediction_error`が残ってverdictは適用されること（promptに予測の指示と対象のtaskが載ること）を確かめる。
