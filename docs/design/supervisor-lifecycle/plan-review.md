# Plan review (supervisor)

[ADR-0044](../../adr/0044-findings-proposals-from-findings-and-quiet-observer.md)の決定10〜15・17（task 281）。submitされたproposalを、supervisorが起動するheadlessのplan review jobが検査し、そのverdictと人のanswerをruntimeが適用する。use caseは`src/application/supervise/plan_review.rs`、storeは`src/infrastructure/plan_reviews.rs`（port `PlanReviewStore`）、verdictの型と順序は`src/domain/plan_review.rs`。run slotは使わず、observerと同じくloopの各passで進める（`--once`のloopは走っているplan reviewを待ち、passでverdictかanswerを適用したらもう1 pass回ってreadyになったtaskをclaimしてから終わる。`--once`で立てたplannerは終わらせない）。drain中（`stop`、provisioningの失敗）は新しいplan reviewを始めず、reviseの配送もしない（走っているjobとanswerの適用は続ける）。

1. **記録**（schema v27、`migrations/0027_plan_review.sql`）: jobは`plan_reviews`の1行（`proposal_id`、`attempt`、`supervisor_token`、`dir`、`started_at`、`finished_at`、`outcome` = `pass` / `revise` / `concern` / `failed` / `interrupted`、`verdict`のJSON、`error`）。未完了の行は部分unique indexで1つまでなので、queue全体で同時に1つ。`proposals`に`review_hold`（`failed` / `concern`: plan reviewが自分では取り直さない）、`revise_reasons`（plannerに渡す指摘のJSON配列）と`revised_at`（差し戻した時刻）、`revise_sent_at` / `revise_planner_id`（配送を取った時刻と渡した相手。nullならまだ渡していない）、`unresponsive_at`を足した。`submit`（出し直しを含む）はこれらをすべて消す。askのkindに`approve_plan`を足した。eventはrun_eventsがtaskかgoalを要るので、proposalの最初のtask（ID最小）に`proposal_id`付きで記録する。
2. **順序**（`next_to_review`）: 対象は`submitted`で`review_hold`が無く、`submitted`のtaskを持つproposal。`interrupt`の優先度のsubmittedのtaskを持つものが先、次にsubmitの古い順、次にID順。gateは飛ばさない。
3. **開始**（`begin_plan_review`、`BEGIN IMMEDIATE`）: 未完了の行があり、そのsupervisorの登録が生きていれば（heartbeatが30秒以内）始めない。そうでない行は`interrupted`で閉じる（supervisorが死んだjobの引き継ぎ）。対象であることを再検査し、行を作って`<queue dir>/plan-reviews/<行のID>/`を`dir`にし、`plan_review_started`（`proposal_id`、`plan_review_id`、`attempt`、`dir`、`session_id`、jobを起動するrepositoryのcheckoutの`cwd`）を記録する。promptを`prompt.txt`に書き、`AgentProvider::headless_command`（Claudeでは`claude -p --allowedTools Read Grep Glob -- <prompt>`）をrepositoryのcheckoutで、`DAGQ_ROLE=reviewer`と`DAGQ_QUEUE`付きで起動し、stdout / stderrを`review.out` / `review.err`に書く。timeoutは`AgentProvider::review_timeout`。
4. **prompt**（`plan_review_prompt`）: 最初にrepositoryのAGENTS.md / CLAUDE.md、`docs/adr/README.md`、taskが名指すADRと設計文書を読んで反映せよと指示する（verificationの規則やADR番号の割り当てをruntimeに埋め込まない）。材料はproposalのtask（全field、依存、goalへの依存）、関係するgoal（description・acceptance・constraints。constraintsがtaskのdescriptionより優先）、`dagq lint`の結果（`domain::lint::lint`）、他の`submitted` / `revising`のproposalとそのtask（このproposalより前に出されたか後か）、`ready` / `in_progress`のtask（200件まで、長いfield付き）、人が答えたask（新しい順に30件、先例の候補）、衝突の多いファイル（`stats`の既定のwindowの`conflict_hotspots`のうち`deleted`でないもの15件まで。renameされたものは今の名前で、`conflicts`・`tasks`・`landings`・`ratio`・`last_conflict_at`・`alert`。supervisorは`LoopSettings.conflicts`（起動時にmain checkoutの`dagq.toml`の`[conflicts]`を読む）とsupervisorの`Repository::main_history`で数える。goal 31）。意味の検査として、重複、実装済み、ADR・constraintsとの矛盾、**acceptanceとdescription・兄弟taskのacceptanceの食い違い**（型を変える変更なのに「tests/cli.rsは変えない」など）、同じファイルを触るtaskの間の依存（とくに衝突の多いファイル）、先に出されたproposalとの食い違い（後に出されたものとの食い違いならこちらは通す）、変える必要のあるreadyのtask（`reopen`）、`in_progress`のtaskは直さず着地後に直すtaskを求める`revise`、lintの指摘を挙げる。同じ種類の指摘に人が答えたaskがあれば、そのIDを`precedents`に入れ、reasonに人の答えを書く。
5. **verdict**（`PlanReviewVerdict`、全体か最外の`{...}`、未知のフィールドは拒否）: `{"verdict": "pass" | "revise" | "concern", "reasons": [...], "summary", "actions": [...], "reopen": [{"task_id", "reason"}], "precedents": [ask id]}`。`actions`は`add_dependency`（`task_id`、`depends_on`）/ `lower_priority`（`task_id`、`priority`）/ `cancel_duplicate`（`task_id`、`duplicate_of`）だけで、`pass`のときだけ適用する。
6. **適用**（`finish_plan_review`、1トランザクション）: 行がまだ自分の未完了の行でなければ何もしない。proposalがもう`submitted`でないか保留されていれば、行を`interrupted`で閉じて何もしない。runtimeは`revise`で`revise_count`が2（`MAX_PLAN_REVISES`、runのreviewと同じ）以上なら`concern`にする（`overridden`）。`precedents`のaskは`precedent: ask N (kind) asked: … — a person answered: …`の行にして、reviseの指摘の後ろとconcernのaskのquestionに足す。
   - `pass`: 各actionを先に検査し（proposalの`submitted`のtaskであること、依存先が存在し自分でないこと、優先度は下げるだけ、重複先がcancelされておらず同じverdictで重複としてcancelされるものでもないこと）、1つでも外れればverdict全体を失敗（下の7）にする。通れば依存を足し（`dependency_added`）、優先度を下げ（`task_priority_changed`、`by: plan_review`）、重複をcancelし（`task_canceled_as_duplicate`、`duplicate_of`）、proposalを`accepted`、submittedのtaskを`ready`にし、draftのgoalを開く。
   - `revise`: proposalを`revising`（taskは`draft`、`revise_count`+1）にし、指摘を`revise_reasons`に置いて配送を待たせる（下の9）。
   - `concern`: `review_hold = concern`にし、`approve_plan`のask（proposalの最初のtask、runなし、`asked_by: plan_review`、options `ready` / `send_back` / `cancel`、questionにsummary・上書きの理由・reasons・先例・`prompt.txt`のpath）を同じトランザクションで作り、適用の後にinboxへ`cmux notify`する。
   - `reopen`（verdictに関わらず）: proposalに無く、`submitted` / `revising`の他のproposalにも属さない`ready`のtaskを`submitted`に戻し（`TaskAction::Reopen`。claimされない）、そのtaskだけの新しいproposal（`revising`、`owner_origin: runtime`、workspaceなし、`revise_count` 0）に入れ、理由を`revise_reasons`に置き、`task_reopened`（`proposal_id`、`reviewed_proposal_id`、`reason`）を記録する。`ready`でないtask（`in_progress`など）と、検査中・差し戻し中のproposalのtaskは変えず、`plan_review_finished`の`reopen_skipped`に理由を残す。出し直し（`submit --proposal`）はproposalの`submitted`のtaskもそのまま持って出す。
   - 最後に行を閉じ、`plan_review_finished`（`proposal_id`、`plan_review_id`、`attempt`、`verdict`、`decision`、`overridden`、`reasons`、`summary`、`actions`、`reopened`、`reopen_skipped`、`precedents`、`ask_id`、`duration_secs`）を記録する。
7. **失敗**（`fail_plan_review`）: 起動できない、非0終了、timeout、stdoutにverdictが無い、verdictを適用できない（許されないaction、proposal内のtaskの`reopen`）は、行を`failed`で閉じ、`review_hold = failed`にして`plan_review_failed`（`code: job_failed`、`proposal_id`、`attempt`、`error`、`duration_secs`、`status: submitted`）を記録する。proposalは`submitted`のまま動かさず、supervisorは同じproposalを自分では取り直さない。`plan_review_failed`はattention（`plan review by hand`）で、`status`の`attention`にも保留が解けるまで出る（`concern`で保留したのに`approve_plan`のaskが自由記述の回答で閉じられたproposalも同じattentionになる）。人の指示で、inboxがtaskを`ready --bypass-review`にするか、plannerかinboxが`dagq submit --proposal N`を打つ。保留中のproposalはtaskとgoalを足さずにそのまま出し直せ（`proposal_resubmitted`、submitの時刻が新しくなる）、plan reviewにかけ直される。
8. **片付け**（`settle_proposals`、各pass）: `submitted`なのに`submitted`のtaskが1つも無くなったproposal（人がbypassで`ready`にした、cancelした）は、jobが走っていなければ、cancelされていないtaskが残れば`accepted`、無ければ`canceled`にし、保留を消して`proposal_settled`を記録する。goalとtaskが他のproposalに入れるようになり、attentionも消える。
9. **reviseの配送**（`tend_planners`、各pass）: plannerが終わったかは`planner_view`で決め、`exited`か`lost`（wrapperのheartbeatが止まった）、または`cmux workspace list`に居ない上でwrapperも死んでいるものだけを終わったとみなす（居ないだけでは証拠にせず、workerと同じくwrapperで判定する）。まず差し戻し中のproposalを見て、渡した相手のplannerが終わっていれば`plan_revise_lost`を記録して未配送に戻し、終わっていないのに`--planner-timeout`（既定3600秒）を過ぎても出し直されていなければ`planner_unresponsive`（`planner_id`、`waited_secs`）を記録する。まだ誰にも渡せていないreviseも、`revised_at`から期限を過ぎれば`planner_unresponsive`（`planner_id: null`）にする。どちらも1回だけで、attentionは`check the planner`、workspaceは閉じない。配送を取ったまま記録の無いもの（supervisorが間で死んだ）は30秒後に未配送に戻す。次に未配送のreviseをproposalのID順に配る。持ち主のworkspace（`owner_workspace_id`）のplannerが生きていれば、`idle`になるのを待ち、`claim_revise`（`revise_sent_at`がnullの行だけを条件付きUPDATEで取る。2つのsupervisorが同じreviseを二重に配らない）で取ってから`plan_revise_request`（指摘、先例、`dagq submit --proposal N`で出し直すこと、意図の変わる修正は人に聞くこと）を`submit_input`で打ち込み、`plan_revise_sent`（`planner_id`、`workspace_id`、`opened: false`）を記録する。打ち込みが失敗すれば取った配送を戻す。持ち主が居ないか終わっていれば、runtimeが立てたplannerで生きているものが`--runtime-planners`（既定1、run slotとは別。人が開いたplannerは数えない）未満のときだけ、配送を取って`open_runtime_planner`で新しいplannerを立て（初期promptに指摘）、`plan_revise_sent`（`opened: true`）を記録する。上限に達していれば待つ。持ち主のworkspaceが一覧に居ないのにwrapperが生きているときも待つ（期限でinboxに届く）。reviseを配った後、同じ上限の残りでruntimeやjobが作ったdraftのplannerを立てる（[Draft planners (supervisor)](draft-planners.md#draft-planners-supervisor)）。
10. **runtimeが立てたplannerの終わり**: runtimeが立てたplannerのうち、終わったものはworkspaceが`cmux workspace list`に居れば閉じ、行を`close_planner`で閉じる。`idle`で、自分宛てのreviseが残っていない（proposalを出し直した）ものには1回だけ`/exit`を送り、終了が記録された後のpassで上のとおり閉じる。`/exit`から`WorkspaceBackend::exit_timeout`を過ぎても終わらなければworkspaceを閉じて行を閉じる。人が開いたplannerはruntimeが閉じない。
11. **answer**（`decide_plan`、1トランザクション）: 回答済み・未closeの`approve_plan`のask（`plan_answers`）のうち、回答が`ready` / `send_back` / `send_back: <理由>` / `cancel`で、askのtaskのproposalがまだ`submitted`で`review_hold = concern`のものに適用する。`ready`はproposalを`accepted`にしてtaskを`ready`、`send_back`は`revising`にして`revise_reasons`を「人がask Nで差し戻した: <理由>」と直近のverdictのreasonsにし（配送は9）、`cancel`はproposalを`canceled`にしてsubmittedのtaskをcancelする。askを閉じて`plan_decided`（`proposal_id`、`ask_id`、`answer`、`status`）を記録する。proposalが動いていればaskを閉じるだけ。それ以外の回答は適用せず、`ask_answered`の`runtime_delivers`が`false`なので`read the answer of ask N and close it`のattentionになる。適用できる回答は`runtime_delivers: true`で、`status`では`applying the answer of ask N (runtime)`。
12. **設定**: `supervise --runtime-planners N`（既定1）、`--planner-timeout SECS`（既定3600）、`--plugin-dir PATH`（runtimeが立てるplannerが読むplugin）。`up`は自分の`--plugin-dir`をsupervisorにも渡す。
13. **test**: `tests/it/plan_review.rs`がstubのheadless provider（台本のverdictを印字する）とcmuxのdoubleで、pass（actionの適用とprompt）、生きているplannerへのrevise（acceptanceとdescriptionの食い違いの指摘と、先例の回答が載ること）と期限切れのinboxへの通知、閉じたplannerの代わりにruntimeが立てるplannerと同時の数の上限（上限で待つreviseの期限切れを含む）、concernのaskとanswer（`ready` / `send_back: 理由` / `cancel`）の適用、reviseの上限超え、jobの失敗と適用できないverdict、保留したproposalの出し直しとbypassによる片付け、interruptの先行、readyのtaskの`reopen`（claimされず、runtimeのplannerが直して出し直す。検査中のproposalのtaskは動かさない）を確かめる。
